# 安全审计与部署边界

审计范围：`dsh-tool-ssh` 0.1.0 的 Cordis 工具层、`ssh2` 传输层、默认 bundle
配置和端到端测试。本次审计于 2026-08-14 完成；生产依赖已执行
`npm audit --omit=dev`，结果为 0 个已知漏洞。该结果不替代服务器、模型和
Harness 本身的安全审计。

## 功能与信任边界

插件把一个模型工具调用转换为对已配置 SSH 别名的非交互式 POSIX shell
执行。模型不能提交裸地址，但一旦某个别名允许任意命令，模型在该远程账号
权限范围内就拥有远程代码执行能力。提示注入、错误的模型授权或可访问工具
调用的恶意用户，都应被视为可能的命令来源。

凭据、目标地址和白名单由 profile 管理员提供；模型只可提供别名、命令、可选
工作目录和超时。所有连接均为一次性连接，未启用 TTY 或 agent forwarding。

## 发现的问题与已实施的缓解

| 编号 | 旧行为 / 风险 | 严重度 | 0.2.0 的处置 |
| --- | --- | --- | --- |
| S-01 | 未配置 `knownHostFingerprint` 时接受任意主机密钥，攻击者可在首次或被劫持连接中实施中间人攻击。 | 高 | `requireHostKeyVerification` 默认 `true`；每个启用别名必须有已带外核验的指纹。 |
| S-02 | 模型可将任意字符串交给远端 shell。别名白名单不能抵御提示注入后的破坏、提权或数据外传。 | 严重 | 每个主机默认需要 `allowedCommands` 的精确匹配；仅可逐台以 `allowUnrestrictedCommands: true` 明确放开。受限模式也限制 `workdir`。 |
| S-03 | profile 可内联密码、私钥和口令，易被版本库、备份、日志或错误配置泄漏。 | 高 | `allowInlineSecrets` 默认 `false`；默认只接受 `passwordEnv`、`passphraseEnv` 和 `privateKeyPath`。 |
| S-04 | 模型可请求极大超时；后台任务文案称无超时；超量输出只丢弃内存内容，远端仍可持续洪泛。 | 中 | 增加前后台默认值和硬上限、命令字节上限；stdout/stderr 触顶会尽力发送 `TERM` 并关闭连接。 |
| S-05 | 认证、连接和私钥读取错误可能包含配置中的裸地址或本地绝对路径，与“模型只见别名”承诺冲突。 | 中 | 对运行时错误统一使用别名和通用原因，不回显远端地址、私钥路径或底层 socket 文本。 |
| S-06 | agent forwarding 未显式禁用，且未配置 agent socket 的失败不清晰。 | 中 | 显式 `agentForward: false`、`tryKeyboard: false`；agent 模式没有可用 socket 会失败。 |
| S-07 | `Capture.take()` 的截断状态会跨后台读取保留，可能反复报告过时的“输出丢失”。 | 低 | 每次读取后重置该增量的截断状态。 |

`MD5:` 指纹仅为兼容旧配置保留；新部署应一律使用 `SHA256:`。它是公钥的
指纹格式，不应与弱口令或旧 SSH 算法兼容性混为一谈。

## 仍然存在的风险

这些风险属于 SSH 远程执行的固有边界，不能只靠客户端插件消除：

- 将 `allowUnrestrictedCommands` 打开等同于给模型该远程账号的完整 shell
  能力。命令白名单也只能约束字符串，无法改变被允许程序自身的权限。
- 取消/超时通过 SSH `TERM` 请求与断开连接实现；守护化、双重 fork、`nohup`
  或已脱离会话的子进程仍可能继续运行。
- 认证成功后远端命令的输出本身可以包含敏感数据；输出上限不构成脱敏。
- `ssh-agent` 仍会使用该 socket 可提供的身份。不要把比目标主机更高权限的
  agent 暴露给运行 Harness 的进程。
- 插件不取代服务器侧审计、账户治理、MFA、密钥轮换或网络分段，也不替代
  dsh Web/API 的访问控制。

## 上线建议

1. 为每台目标创建独立、低权限的服务账号；不要配置 `root` 或可无密码 sudo
   的账号。
2. 在独立可信渠道核验一次 `SHA256` 主机密钥指纹，纳入变更管理；换钥必须由
   运维人员审查，不要通过模型“自动修复”。
3. 先使用精确 `allowedCommands` 和最小 `allowedWorkdirs`；复杂运维操作优先
   做成受服务器端权限控制的脚本或受限子命令。
4. 在服务器 `authorized_keys` 层使用 `restrict`、必要时 `command=` 强制命令，
   并关闭不需要的端口转发、X11 和 PTY；同时用防火墙将来源限制为 Harness
   主机。
5. 将密码和口令放入进程级秘密注入机制或受控环境变量，私钥文件设置为仅
   Harness 账户可读；不要提交 profile、`.env` 或私钥到仓库。
6. 审计 dsh 的可访问用户、会话与工具调用记录，并在服务器保留命令/登录日志。
   对生产别名禁用 `enableRunInBackground`，除非确有受监控的长任务需求。
